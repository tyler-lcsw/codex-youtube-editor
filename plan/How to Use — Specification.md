# How to Use — specification

Provide simple end-user documentation for every current tab, control, option and production skill. Add a native How to Use tab and per-tab help. The document is explanatory help, never a new production policy or a claim that retained tools are qualified.

Use one source: docs/user-guide.json, schema_version 1, title string, articles array. Each article has unique id (lowercase hyphenated), section, title, summary, status, steps [string], notes [string], and optional prompt string. Plain strings only, no markup requirement. Sections in reading order: Getting started; Brief & sources; Understanding; Review; Resources; Codex & QA; How to Use; Production skills; Troubleshooting. Every article must have concrete numbered steps, brief expected result, and practical limits. The current controls, workflow/routes and 18 skill folders are the coverage authority; future research remains labelled planned.

The app renders this source natively and searches titles, summary, steps, notes and prompt. It works with no project or authentication. A section selector narrows the list; Copy example copies a sample prompt without executing it; Reload help rereads the source. Load valid repository docs first, falling back to bundled docs when missing/invalid; show which copy is used and any fallback reason. Validate schema, IDs, required strings and steps. Invalid content never crashes the app. A context Help button opens a sheet filtered to the current tab, preserving the underlying screen and its draft. A Help menu opens the dedicated tab. Standalone HTML is generated from the same JSON for users outside the app; no remote libraries.

Content must explain saved vs unsaved fields, source vs reference links, exact resolution transitions, prerequisites/evidence, each provider route, the separate model picker, authentication recovery, approvals, interruptions, QA findings, local diagnostic paths, missing/changed media and software limitations. Explain that most media features are requested through Codex rather than individual app buttons. For every skill give inputs, a short example request, result and qualification limits. No terminal commands in the main how-to steps. No publication tests/uploads, implicit model downloads, hosted generation or creative certification.

After documentation is complete, assess a tutorial video. Prepare a practical storyboard based on verified instructions. Do not demonstrate unavailable abilities as working or use every skill merely to fill a checklist. Actual media production, if chosen, must follow the production rules with before/during/after QA and actual audiovisual review.
