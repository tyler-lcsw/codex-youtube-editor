# Codex YouTube Editor — Design and Research

Prepared September 5, 2026. Status: proposed design; implementation has not started. Method: Superpowers brainstorming and writing-plans, adapted to the requested planning-only deliverable. Target chosen by Tyler: **local Apple M4 Mac (m4-mini.local) with 24 GB unified memory, with an optional additional GPU worker**. Remotion retention is a confirmed requirement.

## Recommendation

Build a Codex-native workflow around the existing editing engine. Preserve its cut editor, timeline formats, Remotion components, media library, review process, and publishing tools. Put replaceable media providers behind small, explicit interfaces. Default production media processing to local providers. Add an approved hybrid image workflow: propose GPT Image 2 through Codex for bounded thumbnail and standalone image work, and prefer local providers when generation is tightly integrated into a larger pipeline. Other cloud integrations remain explicitly selected exceptions.

Recommend GPT-6 Astra for complex editorial and visual work, while treating GPT-5.6 Sol as a fully supported operating model. Both must complete the same acceptance suite. Codex supplies judgment and code authoring; deterministic tools perform timing, rendering, validation, and job management. Do not introduce a second hidden LLM editing service.

Local alternatives exist for all the major capability categories. **Equivalent output quality is a release criterion to demonstrate, not a fact established by finding a model repository.** Difficult noise, filler retention, presenter likeness, and avatar quality are the highest-risk comparisons. A feature does not count as migrated if it silently substitutes a generic voice, a still image, a stock clip, or a cloud call for the requested operation.

## Three possible approaches

| Approach | Advantages | Limits | Decision |
|---|---|---|---|
| Rename instructions and swap API calls in place | Small initial patch | Leaves timing assumptions, host dependencies, scattered provider logic, and no parity proof | Insufficient for the request |
| Codex-native skills plus provider adapters around the current engine | Preserves useful code and upstream mergeability; supports local and optional cloud execution | Requires contracts, capability tests, and staged migration | **Recommended** |
| Rewrite the editor and renderer around an entirely different open source stack | Can eliminate Remotion's custom license | Existing TSX shots and future Remotion changes require conversion; large quality and maintenance risk | Rejected for this fork: Tyler explicitly requires retaining Remotion |

### Licensing decisions that affect the architecture

Qwen ASR/alignment/TTS/image candidates, Wan and InfiniteTalk publish Apache-2.0 model cards; MOSS-SoundEffect and its audio tokenizer also publish Apache-2.0 cards. ACE-Step's selected model card and Chatterbox's card state MIT. Audit the exact full dependency graph before shipping, including converted weights, face detectors, vocoders and alignment models. The license of a UI or Python package does not cover every downloaded checkpoint.

Do not default to MMAudio merely because its code is MIT: its checkpoints are CC-BY-NC-4.0. Tango's published weights are also noncommercial. These are poor defaults for a general YouTube creator tool. [MMAudio license distinction](https://github.com/hkchengrex/MMAudio#license), [Tango card](https://huggingface.co/declare-lab/tango).

Remotion is source-available under a custom license. Its version-4 license permits free use for individuals, qualifying small organizations and other listed cases, but does not grant unrestricted open source redistribution rights. **Confirmed scope: retain Remotion and its TSX ecosystem; use open source media providers alongside Codex orchestration and approved hybrid image generation.** Renderer replacement is out of scope. Document the applicable Remotion terms accurately and do not describe the entire stack as unrestricted open source. Tyler specifically wants the Codex Remotion plugin and relevant skills used where helpful. Verify their actual installed availability and instructions during setup, then apply them to authoring and rendering without introducing conflicting copies of project skills. [Pinned Remotion license](https://github.com/remotion-dev/remotion/blob/v4.0.486/LICENSE.md).

Audit bundled SFX/music separately: retaining previously generated assets requires no new paid generation, but it does not change their origin. A clean local-generated starter library can replace them by stable catalog IDs once listening tests pass. Retain provenance of any reused assets.

## Approved hybrid image workflow

The fork supports two explicit profiles: **local** for local media inference, and **hybrid** for selected hosted operations with user approval. In hybrid mode, recommend GPT Image 2 through Codex for packaging and straightforward image work when the native capability is available. This is a deliberate product feature; the complete local image path remains supported. Approval to include this policy in the plan does not authorize generating images or transmitting reference photos now.

| Image workflow | Recommended route | Reason |
|---|---|---|
| Standalone thumbnail, three packaging bets, promo still or a few interactive edits | Propose native Codex image generation; execute within approved scope | Fits the editorial conversation and direct visual review; avoids requiring a large local model installation just to make a thumbnail |
| Elaborate thumbnail with several references or complex artwork | Still consider Codex first if its exposed capabilities satisfy the request | Visual complexity alone does not require a local pipeline |
| Repeated programmatic generation with control maps, masks/layers, pinned model settings, or shot-to-shot dependencies | Local model on Mac or qualified GPU worker | Pipeline control, restartability and consistent settings matter more than a convenient one-off generation |
| Large unattended batches or tightly coupled image-to-video/animation workflows | Prefer local after checking required capabilities and hardware | Avoids repeated agent-mediated handoffs; keeps intermediate operations in one resumable workflow |
| A few approved Codex key images feeding a local video or compositing pipeline | Hybrid: generate, review and import, then continue locally | Reuse strong key assets without making every downstream operation hosted |

These are routing recommendations, not rigid asset-count thresholds. A small batch alone does not require an API or local model. Explain the proposed route using the actual requirements and let the user choose. Unsupported native controls must be surfaced rather than silently approximated. Local handoff also requires a qualified provider; it is not a guarantee of superior identity consistency or output quality.

**Approval contract.** Before a hosted operation, describe the provider, intended output, exact reference assets to be transmitted, and a bounded scope such as three thumbnail bets plus two edit rounds. State known usage constraints; do not imply that no API key means free or unlimited usage. Record the user's approval and scope in project state. Reuse it for operations within that scope; request a new decision for a different provider, additional reference assets, changed purpose, or work beyond the approved bounds. Strict local mode blocks native hosted image generation. Declining a proposed route returns a local option and its actual hardware requirements.

**Native Codex integration.** Prefer the built-in image tool, with GPT Image 2 as the requested target. The locally inspected tool exposes prompts and reference inputs but no model-selection argument. Check runtime availability and any reported model information; record the actual reported model or “unknown,” and never claim that the tool forcibly selected GPT Image 2 without evidence. If that model is a hard requirement and cannot be verified, surface the mismatch before execution. Tool availability is separate from choosing Astra or Sol. Do not silently substitute another image model or switch to a separately billed API/CLI path. A separate API route needs its own explicit approval.

**Durable handoff.** Implement an agent-mediated native request, not a Python worker pretending it can invoke a desktop tool. Save an image request and approval reference, enter `awaiting_approval` or `awaiting_codex_image`, and let the Codex skill perform the approved generation. Copy the resulting image into a versioned project asset directory before marking success. Import validates the actual file, dimensions, format and hash; preserve prompt, selected reference hashes, approval scope, provider and reported model provenance. Reuse the same normalized image result, thumbnail specification, PNG/JPG export, brand/text checks and downstream timeline handoff as local providers. Resume reconciles existing output receipts before generating again, so an interrupted import does not consume another approved generation accidentally.

Do not require a Qwen download to begin a hybrid thumbnail session. Keep local setup independently available and retain its full parity release gate. Hosted-image success cannot stand in for validation of the local replacement. Generalize the policy contract for future approved hybrid resources, but enable only explicitly configured capabilities; this image exception does not authorize hosted audio or video.

## Provider contracts and timing

Keep existing JSON shapes readable. Add a schema version and optional metadata without gratuitously replacing `cuts.json`, `timeline.json`, `sfx-plan.json`, `music-plan.json`, `vo-manifest.json` or `edited-transcript.json`. Read legacy files; preserve unknown fields when updating. Separate native provider responses from the normalized artifacts consumers read.

Each provider declares task types, input kinds, languages, sample rates/resolutions, duration limits, reference-image/voice support, devices and installed model revision. Jobs return local artifact paths plus provenance and measured properties. Unsupported operations fail before execution; a cloud fallback requires explicit selection. Hash inputs, prompt, provider revision and settings for resume/caching; cache keys must change when any of these change. Seed recording supports repeatability but does not promise bit-identical generation across devices.

Transcript words retain `text`, integer `start`/`end` milliseconds and stable source identity. Recognition confidence and alignment confidence are separate nullable fields; never invent 1.0 confidence for missing values. Keep source transcripts immutable and corrections explicit. Proper nouns, fillers, overlap, unknown language aligners, and untimed tokens must surface for review. Segment acoustic features such as pauses, energy and pitch can help Codex infer emphasis. Optional local audio understanding may enrich these signals, but must not present inferred emotion as fact. The inspected AssemblyAI call does not request a dedicated emotion-analysis output, so the video's tone claims are not an extra field that can simply be copied.

Build the remapper from the **actual render segment manifest**, after `plan_clip` applies pause compression and padding. Raw keep ranges alone are insufficient. Map clip-relative source samples to output samples/frames using rational FPS and explicit rounding. Include repeated/reordered clips, boundaries, tokens split by cuts and audio pickups. Transition overlap must have a defined time policy.

Keep an independent ASR pass over the final render for QA: a time remapper cannot discover speech that survived an unintended cut. The current verifier's growing drift budget can hide real errors. Stream duration equality also cannot prove lip sync. Validate start PTS, sample/frame counts, fixed drift tolerances, and early/middle/late audiovisual landmarks.

## Mac runtime and optional worker

Use native Mac Python/Node/FFmpeg and native MLX/MPS workers where supported. Avoid placing Apple GPU inference in Linux Docker. Separate audio, image and video environments because their PyTorch/Transformers requirements can conflict. Install the small editing core first; fetch selected models explicitly after displaying disk requirements and license provenance. Pin the Python lock and Remotion package family together; use a currently supported Node LTS verified against the lock, rather than the README's Node 18 minimum.

The project is based directly on **m4-mini.local**, the M4 running this Codex instance. Live verification confirmed arm64, model identifier Mac16,11, 25,769,803,776 bytes of memory (24 GiB), and the local workspace `/Users/tyler-lcsw/projects/yt-codex`. The plan files are already present here; this directory is not yet a Git checkout. M4 owns the source checkout, project state, assets, orchestration and local rendering/inference. MBP has no control role: do not establish MBP-to-M4 SSH, Remote Control, credentials, tunnels or a controller dependency. No MBP access or permission changes are needed for this project. Free disk and installed runtime readiness remain ordinary local setup checks. Any additional GPU worker is optional, unselected and coordinated from M4 only when explicitly configured.

Use 24 GB as the initial total memory budget shared with the OS and rendering processes, not as 24 GB available model memory. Start with sequential inference and bounded render concurrency; trial smaller audio models and qualified quantized image candidates before selecting defaults. Record peak memory, memory pressure, swap growth, elapsed time and render responsiveness. Do not promise full image/video/avatar parity on this hardware before measuring. An additional worker remains a conditional option for workloads that fail the memory, quality or practical runtime trials; qualify its backend independently. Unified memory is not equivalent to CUDA VRAM. [Wan model card](https://huggingface.co/Wan-AI/Wan2.2-TI2V-5B).

The worker is optional for operating the editor; on constrained Macs it can become necessary for practical full generative parity. No capability should be silently dropped because the worker is absent. Setup must state which selected workloads can run locally, which are slow, and which need additional compute. Do not claim full Mac-only parity on an unspecified machine.

`doctor` probes actual codecs and runs a tiny encode. Prefer VideoToolbox on eligible Macs, NVENC on qualified NVIDIA workers, and libx264/libx265 CPU fallback. Merely detecting Linux is not evidence of CUDA. Preserve 10-bit delivery where selected and supported, plus a broadly playable 8-bit H.264 review output. Handle spaces/Unicode paths, source 29.97/59.94 FPS, variable-frame-rate inputs, and source dimensions explicitly. Upstream PR #1 addresses Mac encoders, but is open and conflicted at inspection; review and adapt it rather than assuming it solves all portability issues. [PR #1](https://github.com/hassancs91/claude-youtube-editor/pull/1).

Use one job at a time per heavy model/device initially. Worker requests contain allowlisted task data and content-addressed assets, never arbitrary shell commands. Bind locally or use authenticated private transport. Retry boundedly; cancellation and worker loss leave resumable local manifests. No worker deployment or purchase is authorized by this plan.

In the strict local profile, production media workers must complete after models/fonts/browser binaries are cached, with external network denied. Approved hybrid image generation occurs through Codex outside that worker boundary and returns a validated local artifact; selected references are transmitted to the hosted service. Codex itself remains online, and may receive transcripts and review frames as part of its work; this is **local media inference**, not an offline or zero-disclosure AI workflow. Web capture, YouTube, and optional Notion/cloud adapters are separately explicit network operations. Disable hosted prompt expansion and remote custom-node services in local workflows.
